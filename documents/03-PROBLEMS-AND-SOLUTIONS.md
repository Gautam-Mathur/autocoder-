### Problem: WebContainer npm Install Timeout

**Symptoms**: Pre-warm fails with "npm install timed out after Xs, killing". Retry also fails.

**Root Cause**: WebContainer's npm is slower than native npm. Cold cache installs can take 2-4 minutes for the core batch (21 packages + all transitive dependencies). The original timeout (60s) was far too aggressive.

**Solution**: 
- Core batch timeout increased to 300s (5 minutes) with 180s stall timeout
- Later batches get 180s timeout / 90s stall timeout (they benefit from cached transitive deps)
- Tab visibility detection pauses the stall timer when the browser tab is hidden (WebContainer throttles background tabs)
- Retry logic clears `node_modules` and `package-lock.json` before retrying
- Progress feedback shows package count and percentage so users know it's working

**Files**: `client/src/lib/code-runner/webcontainer.ts`

**Impact**: Pre-warm success rate went from ~60% to ~95% on typical network connections.

### Problem: npm "warn config optional" Messages

**Symptoms**: Console flooded with `npm warn config optional Use --omit=optional to exclude optional dependencies`.

**Root Cause**: Newer npm versions (npm 9+) deprecated the `--no-optional` flag in favor of `--omit=optional`.

**Solution**: Changed npm install flags from `--no-optional` to `--omit=optional` across all pre-warm and auto-run install commands.

**Files**: `client/src/lib/code-runner/webcontainer.ts`

### Problem: Vite Crashes on Missing tsconfig.node.json

**Symptoms**: Generated projects fail with `ENOENT: no such file or directory, open 'tsconfig.node.json'`.

**Root Cause**: Vite's `tsconfig.json` template includes `"references": [{ "path": "./tsconfig.node.json" }]` but the referenced file was never generated by CodeGen V2.

**Solution**: CodeGen V2 orchestrator now generates both `tsconfig.json` and `tsconfig.node.json` as part of config file generation. The `tsconfig.node.json` includes `"compilerOptions": { "composite": true, "module": "ESNext", "moduleResolution": "Node" }`.

**Files**: `server/modules/codegen-orchestrator.ts`

### Problem: Toast System Mismatch Causes Auto-Runner Patching

**Symptoms**: Auto-runner's pre-flight check detects toast files don't match expected format, triggers patching that can break other generated code.

**Root Cause**: The auto-runner has a `CRITICAL_UI_FILES` list with expected file contents. Generated toast files used Radix Toast primitives instead of the standalone pattern the auto-runner expects. This caused the auto-runner to overwrite the generated files with its own versions, breaking imports in other components.

**Solution**: 
- Toast files (`use-toast.ts`, `toaster.tsx`) now exactly match the auto-runner's expected format
- Use `// @generated` marker that auto-runner recognizes
- Self-contained global state (no Radix dependency in toast)
- Standalone `toast` export for direct use without hooks
- Auto-runner only patches if files don't already contain the `@generated` marker

**Files**: `server/modules/codegen-orchestrator.ts`, `client/src/lib/code-runner/auto-runner.ts`

**Lesson learned**: When multiple systems (generator + runner) both write files, they must agree on the exact file format or use markers to avoid conflicts.

### Problem: npm Re-downloads Packages That Were Pre-warmed

**Symptoms**: Even with pre-warm complete, `npm install` during auto-run downloads packages again, taking extra time.

**Root Cause**: Package versions in generated `package.json` (e.g., `"react": "^18.2.0"`) didn't exactly match pre-warmed versions (e.g., `"react": "18.3.1"`). npm resolves `^18.2.0` as a different install requirement than `18.3.1` and re-downloads even when the installed version satisfies the range.

**Solution**: 
- Synced `AVAILABLE_DEPS` and `DEV_DEPS` in code generation modules to use the exact same version strings as `PREWARM_BATCHES` in `webcontainer.ts`
- Generated `package.json` uses exact versions (no `^` or `~` prefixes) for all pre-warmed packages
- Added a version synchronization check in the validator

**Files**: `server/modules/codegen-orchestrator.ts`, `client/src/lib/code-runner/webcontainer.ts`

### Problem: Pipeline Crashes on Null plan.entities

**Symptoms**: `TypeError: Cannot read properties of null (reading 'map')` during code generation.

**Root Cause**: Some conversation flows produce plans without an `entities` array (e.g., simple utility apps, calculators, single-page tools). The pipeline assumed `plan.entities` was always a non-null array.

**Solution**: 
- Added null safety (`plan.entities || []`) throughout `plan-driven-generator.ts` and `pipeline-orchestrator.ts`
- All pipeline stages that access `plan.entities`, `plan.pages`, `plan.apiEndpoints`, and `plan.workflows` now use optional chaining and default empty arrays
- Added explicit type checking before iterating over plan arrays

**Files**: `server/modules/plan-driven-generator.ts`, `server/modules/pipeline-orchestrator.ts`

### Problem: 40-Batch Pre-warm Takes Too Long

**Symptoms**: Pre-warming 140 packages via 40 sequential batches takes 10-15 minutes because each batch rewrites the cumulative `package.json` and runs full npm resolution.

**Root Cause**: The cumulative approach means batch 40 resolves all 140 packages even though batches 1-39 already resolved most of them. Each npm run has fixed overhead: tree building, lock file computation, `node_modules` scanning. With 40 batches, this overhead is multiplied 40x.

**Solution**: Consolidated 40 batches into 4 tiered batches (core, ui, server, extras). npm resolution runs 4 times instead of 40, eliminating 36 redundant passes. Total pre-warm time dropped from 10-15 minutes to 2-4 minutes.

**Files**: `client/src/lib/code-runner/webcontainer.ts`

### Problem: Native Binary Packages Crash WebContainer

**Symptoms**: npm install fails with compilation errors for packages like `sharp`, `better-sqlite3`, `bull`, `ioredis`. Errors reference `node-gyp`, `gcc`, or `make`.

**Root Cause**: These packages require native C/C++ compilation (node-gyp) which WebContainer doesn't support. WebContainer runs a JavaScript-only Node.js implementation in the browser.

**Solution**: 
- Removed native packages from `PREWARM_BATCHES`
- Added an explicit `NATIVE_ONLY_PACKAGES` blocklist in the pre-warm system
- Dependency resolver automatically excludes native packages when targeting WebContainer
- These packages remain fully supported in Electron mode via native npm

**Affected packages**: `sharp`, `better-sqlite3`, `bull`, `ioredis`, `canvas`, `bcrypt` (use `bcryptjs` instead)

**Files**: `client/src/lib/code-runner/webcontainer.ts`, `server/modules/dependency-resolver.ts`

### Problem: Generated Imports Reference Non-existent Files

**Symptoms**: Runtime error `Module not found: Can't resolve './components/ui/data-table'`.

**Root Cause**: CodeGen V2 page builder imports components that the component library declares but the orchestrator didn't include in the output files. This happens when the page builder selects a UI pattern (e.g., Table view needs DataTable) but the orchestrator only generates the page file, not the supporting component files.

**Solution**: 
- The validator (`codegen-validator.ts`) now traces every import chain from every file
- Missing imports trigger stub file generation with expected exports
- The orchestrator was updated to include all component dependencies recursively
- `validateAndFix` runs in multiple passes until no more auto-fixable issues remain

**Files**: `server/modules/codegen-validator.ts`, `server/modules/codegen-orchestrator.ts`, `server/modules/pipeline-orchestrator.ts`

### Problem: Large package.json Fails in WebContainer

**Symptoms**: Writing `package.json` fails or npm install stalls for generated projects with many dependencies.

**Root Cause**: WebContainer has a file size limit for write operations. Projects with 100+ dependencies produce `package.json` files exceeding 15KB, which can cause write failures or extremely slow npm resolution.

**Solution**: Auto-runner detects large `package.json` (>15KB) and switches to a batched install strategy:
1. Write a minimal `package.json` with core dependencies only
2. Run `npm install`
3. Incrementally add remaining dependencies in smaller batches
4. Restore the full `package.json` after all installs complete

**Files**: `client/src/lib/code-runner/auto-runner.ts`

### Problem: Learning Engine Loses Field Types on Merge

**Symptoms**: Entity patterns initially have full `fieldTypes` (e.g., `{ id: "serial", name: "text", createdAt: "timestamp" }`) but after updates, `fieldTypes` becomes empty or incomplete.

**Root Cause**: The `learnEntityPattern` function merged entity patterns by overwriting properties. When a new observation of the same entity had fewer fields, the merge would lose existing field type data instead of preserving it.

**Solution**: 
- Enhanced `learnEntityPattern` to preserve existing `fieldTypes` during merges using `Object.assign(existing.fieldTypes || {}, newFieldTypes)`
- New field types supplement existing ones rather than replacing them
- Added type inference for field names: names ending in `Id` → `integer`, ending in `At` → `timestamp`, ending in `Date` → `date`, common money fields → `decimal`
- Result: 680 out of 716 entity patterns now have full field types (95%)

**Files**: `server/modules/generation-learning-engine.ts`

### Problem: Domain Patterns Missing Domain IDs

**Symptoms**: Domain-mapping patterns were stored without a `domainId` property, making it impossible to filter patterns by industry domain.

**Root Cause**: The `learnDomainMapping` function recorded domain names, entities, and KPIs but didn't extract and store a normalized `domainId` from the input data.

**Solution**: 
- Enhanced `learnDomainMapping` to extract `domainId` from input data using keyword matching
- Added relationship storage from foreign key field analysis
- Merged entity and KPI data instead of overwriting on duplicate domain entries
- Created `seed-domain-knowledge.ts` to seed comprehensive data for all 14 industries
- Result: 3,588 out of 3,700 domain patterns now have `domainId` (97%)

**Files**: `server/modules/generation-learning-engine.ts`, `scripts/scripts/seed-domain-knowledge.ts`

### Problem: Entity Suggestions Missing PlannedEntity Properties

**Symptoms**: TypeScript error: `Type '{ name, fields }' is missing properties 'tableName', 'relationships'` when learning engine suggests new entities.

**Root Cause**: The `applyLearnedPatterns` function pushed entity suggestions into `enhancedPlan.dataModel` with only `name` and `fields`, but the `PlannedEntity` type requires `tableName` and `relationships` properties as well.

**Solution**: Added `tableName` (derived from entity name + 's' suffix, lowercased) and `relationships: []` to all suggested entity objects:
```typescript
enhancedPlan.dataModel.push({
  name: suggestedEntity,
  tableName: suggestedEntity.toLowerCase() + 's',
  fields,
  relationships: []
});
```

**Files**: `server/modules/generation-learning-engine.ts`

### Problem: Background Tab Causes False Timeout

**Symptoms**: Pre-warm times out even on fast connections if the user switches to another browser tab during installation.

**Root Cause**: Modern browsers throttle JavaScript execution in background tabs. WebContainer's npm process continues running but the stall detection timer keeps ticking without receiving progress updates, triggering a false timeout.

**Solution**: 
- Added `document.visibilitychange` event listener
- When tab is hidden, stall timer is paused
- When tab becomes visible again, stall timer resumes
- Stall timeout only counts "visible" time, not total elapsed time

**Files**: `client/src/lib/code-runner/webcontainer.ts`

---

### Problem: Cross-Origin Isolation Breaking Third-Party Scripts

**Symptoms**: Third-party scripts (analytics, CDN resources) fail to load with CORS errors when cross-origin isolation headers are active.

**Root Cause**: WebContainer requires `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` headers. These headers block loading of any cross-origin resource that doesn't opt in via `Cross-Origin-Resource-Policy: cross-origin`.

**Solution**: 
- CDN scripts (React, Babel for preview) are proxied through the Express server via `/api/preview-scripts/:lib`
- The proxy fetches the script from CDN and serves it with correct CORS headers
- 24-hour cache on proxied scripts reduces CDN load

**Files**: `server/routes.ts`, `server/vite.ts`

---

### Problem: Pre-warm Snapshot Corruption

**Symptoms**: WebContainer fails to mount the pre-warm snapshot with parse errors or missing files.

**Root Cause**: The compressed snapshot file (`/cache/prewarm-snapshot.json.gz`) was generated with an older package set and became stale when new packages were added to `PREWARM_BATCHES`.

**Solution**: 
- Added `generate-prewarm-snapshot.ts` script that regenerates the snapshot from current `PREWARM_BATCHES`
- Snapshot includes version hash for cache invalidation
- If snapshot hash doesn't match current batch versions, the system falls back to live npm install
- Snapshot regeneration is part of the CI/deployment pipeline

**Files**: `scripts/scripts/generate-prewarm-snapshot.ts`, `client/src/lib/code-runner/webcontainer.ts`

## Debugging Tips

### Check Pre-warm Status
Open browser DevTools console and look for lines starting with `PreWarm`. The structured logger shows timestamps, timers, and detailed npm output.

### Check Generated Files
```
GET /api/conversations/:id/files
```
Returns all generated files for a conversation with path and content.

### Run CodeGen V2 Tests
```bash
npx tsx -e "import { runAllTests } from './server/modules/codegen-e2e-test'; console.log(runAllTests().summary);"
```
Runs all 3 e2e scenarios (Hospital, E-commerce, Project Manager) and reports errors/warnings.

### Check Pipeline Execution
```
GET /api/conversations/:id/transparency
```
Returns the full pipeline execution report with stage timings, quality scores, and decisions.

### Check Learning Engine Stats
```
GET /api/learning/stats
```
Returns pattern count, preference count, outcome count, and last update time.

### View Server Logs
```
GET /api/logs?level=error&limit=50
```
Returns recent server logs filtered by level. Use `level=warn` for warnings, `level=error` for errors.

### Check AI Mode
```
GET /api/health
```
Returns current AI mode (`cloud` or `local`) and server status.

### Export Learning Data
```
GET /api/learning/export
```
Downloads the complete learning data as JSON for inspection or backup.

### Database Query
Use the PostgreSQL console or Drizzle Studio to inspect database tables:
```sql
SELECT COUNT(*) FROM conversations;
SELECT COUNT(*) FROM project_files WHERE conversation_id = 1;
SELECT * FROM generation_logs ORDER BY created_at DESC LIMIT 10;
```

### Common Error Patterns

| Error | Likely Cause | Solution |
|-------|-------------|----------|
| `Module not found` | Missing component file | Run validator: check `codegen-validator.ts` |
| `npm install timed out` | Slow network or throttled tab | Increase timeout or check network |
| `Cannot read properties of null` | Null plan fields | Check plan generation with `GET /api/conversations/:id/plan` |
| `COOP/COEP header missing` | Server config issue | Check `server/vite.ts` headers |
| `WebContainer not supported` | Incompatible browser | Use Chrome 90+ or Electron mode |
| `Database connection failed` | Missing DATABASE_URL | Check environment variables |
| `Learning data corrupt` | Invalid JSON in learning-data.json | Re-export via `POST /api/learning/save` |
